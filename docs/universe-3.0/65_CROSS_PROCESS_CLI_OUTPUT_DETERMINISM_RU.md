# Побайтная воспроизводимость CLI на неизменном паспорте

**Серия:** UNIVERSE 3.0 / GIZA PRIME  
**Документ:** 65  
**Дата:** 2026-11-25  
**Статус:** два межпроцессных сценария добавлены; полный CI-набор прошёл  
**Назначение:** проверить, что неизменные входные байты дают одинаковые коды завершения, stdout и stderr при отдельных запусках CLI с различными значениями PYTHONHASHSEED.

---

## 0. Исходная задача

Документ 64 закрепил порядок обхода Schema references и перечислил следующий контроль: повторный запуск CLI на неизменном входном паспорте с проверкой стабильности диагностик.

Обычного повторения функции внутри одного процесса недостаточно. Внутри процесса сохраняются один и тот же hash seed и часть состояния интерпретатора. Поэтому новая проверка выполняет CLI в нескольких независимых процессах Python с разными фиксированными значениями PYTHONHASHSEED.

Цель — проверить не только одинаковый итоговый статус, но и точное совпадение выходных байтов.

## 1. Созданный тестовый артефакт

Добавлен файл:

- tests/giza_spatial/test_cli_determinism.py

В нём два межпроцессных сценария. Они используют только синтетический манифест и синтетическую схему; архивные измерения Гизы не задействованы.

## 2. Что именно сравнивается

Для каждого запуска сохраняется тройка:

1. код завершения процесса;
2. полная последовательность байтов stdout;
3. полная последовательность байтов stderr.

Тест считает результаты одинаковыми только при точном совпадении всех трёх составляющих. Сравнение декодированных строк или отдельных фрагментов не заменяет байтовую проверку.

Для каждого набора выполняются отдельные процессы с PYTHONHASHSEED:

- 1;
- 73;
- 987654321.

Входные файлы создаются один раз до серии запусков. Их SHA-256 рассчитывается до первого запуска и после последнего. Тест завершается ошибкой, если CLI изменил байты манифеста или переданной схемы.

## 3. Сценарий A: корректный неизменный паспорт

Создаётся минимальный манифест:
- версия схемы 1.0;
- заполненные идентификатор и название проекта;
- пустой массив datasets.

Для такого шаблона валидатор должен:
- выдать предусмотренное предупреждение об отсутствии наборов данных;
- завершиться успешно;
- вывести итог VALID;
- не сформировать stderr.

Все три отдельных процесса получают одни и те же байты. Проверка подтверждает равенство кодов завершения, stdout и stderr.

Этот сценарий проверяет стабильность положительного ответа и предупреждения на допустимом пустом шаблоне.

## 4. Сценарий B: несколько недопустимых ссылок Schema

Создаётся тот же тип минимального манифеста, но к нему передаётся отдельная синтетическая схема с двумя внешними ссылками:
- одна расположена в $defs;
- вторая расположена в properties.

Политика валидатора запрещает внешние Schema references. Важен не только отказ, но и то, какая из нескольких ошибок будет выведена первой.

Ожидаемый первый адрес:

$.$defs.first_definition.$ref

Поскольку порядок обхода schema-bearing keywords закреплён упорядоченными последовательностями, первым должен обнаруживаться путь внутри $defs, независимо от значения hash seed процесса.

Для всех трёх запусков проверяются:
- код завершения 2;
- отсутствие stdout;
- одинаковое сообщение об отказе в stderr;
- один и тот же первый путь ошибочной ссылки;
- неизменность байтов манифеста и схемы.

Внешние ссылки не загружаются из сети: тест проверяет штатный отказ до обращения к удалённым документам.

## 6. Исправления, обнаруженные в ходе проверки

Первый прогон выявил ошибку в ожидаемом тестом пути: проверка ожидала символ #, тогда как реальная диагностика валидатора использует корневой маркер $.

Следующий прогон обнаружил ещё одно устаревшее ожидание в ранее существовавшем тесте: ожидались кавычки вокруг значений quality, хотя CLI выводит значения статуса без кавычек. Ожидания теста приведены к фактическому контракту вывода.

Это были ошибки тестовых утверждений. После их исправления полный набор из 66 тестов завершился успешно. Код валидатора для этих двух исправлений не изменялся.

История запусков сохраняет и неуспешные промежуточные результаты, и окончательный подтверждённый результат. В итоговый статус включён только запуск 45667120493.

## 7. Что доказано и что не доказано

Подтверждено:
- для двух выбранных классов входа CLI выдаёт побайтно одинаковые результаты в трёх отдельных процессах;
- успешный результат и диагностический отказ не меняются при использованных значениях PYTHONHASHSEED;
- входные файлы остаются неизменными;
- первый отказ на нескольких внешних ссылках Schema воспроизводится;
- полный CI-набор на GitHub-hosted Ubuntu runner с Python 3.11 прошёл.

Не подтверждено:
- идентичность результатов во всех версиях Python и всех операционных системах;
- стабильность каждого возможного сообщения при любых повреждениях манифеста;
- эквивалентность локальных и сетевых файловых систем;
- корректность реальных приборных данных, калибровки или координат;
- физическая правильность модели сооружения и основания.

Результат относится к программной воспроизводимости перечисленных сценариев, а не к достоверности исторической реконструкции или физической гипотезы.

## 8. Следующая техническая граница

Следующий слой — расширить межпроцессную матрицу на остальные существенные ветви CLI:

1. синтаксически повреждённый JSON, повторяющиеся ключи и числовые overflow/underflow;
2. ошибки структурной и семантической проверки манифеста;
3. несколько ошибок и предупреждений в одном паспорте;
4. режим --verify-files с синтетическими файлами, контрольными суммами и проверкой неизменности исходников;
5. сравнение результатов в заявленных поддерживаемых средах выполнения.

После расширения матрицы программный приёмник можно считать воспроизводимым только в проверенных пределах. Следующая независимая граница останется эмпирической: получение первичных временных рядов, полевых метаданных, калибровок и документированной геодезической привязки.
