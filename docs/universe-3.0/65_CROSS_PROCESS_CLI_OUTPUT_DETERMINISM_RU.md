# Побайтная воспроизводимость CLI на неизменном паспорте

**Серия:** UNIVERSE 3.0 / GIZA PRIME  
**Документ:** 65  
**Дата:** 2026-11-25  
**Статус:** пять межпроцессных сценариев реализованы; полный CI-набор из 69 тестов прошёл  
**Назначение:** проверить, что неизменные входные байты дают одинаковые коды завершения, stdout и stderr при отдельных запусках CLI с различными значениями PYTHONHASHSEED.

---

## 0. Исходная задача

Документ 64 закрепил порядок обхода Schema references и поставил следующий контроль: повторный запуск CLI на неизменном входном паспорте с проверкой стабильности диагностик.

Повторение функции внутри одного процесса недостаточно. Внутри процесса сохраняются один и тот же hash seed и часть состояния интерпретатора. Поэтому проверка запускает CLI в нескольких независимых процессах Python с разными фиксированными значениями PYTHONHASHSEED.

Цель — проверить не только одинаковый итоговый статус, но и точное совпадение выходных байтов.

## 1. Созданный тестовый артефакт

Файл: tests/giza_spatial/test_cli_determinism.py

Все сценарии используют синтетические манифесты, синтетическую JSON Schema и тестовый файл. Архивные измерения Гизы не задействованы.

## 2. Метод сравнения

Для каждого запуска сохраняется тройка:

1. код завершения процесса;
2. полная последовательность байтов stdout;
3. полная последовательность байтов stderr.

Результаты считаются одинаковыми только при точном совпадении всех трёх составляющих.

Каждый тест выполняет отдельные процессы с PYTHONHASHSEED:
- 1;
- 73;
- 987654321.

Входные файлы создаются один раз до серии запусков. Их SHA-256 рассчитывается до первого запуска и после последнего. Проверка контролирует неизменность манифеста, переданной схемы и защищённых исходных файлов.

## 3. Проверенные сценарии

### 3.1. Корректный неизменный паспорт

Минимальный манифест содержит версию схемы 1.0, идентификатор и название проекта, а массив datasets пуст.

Ожидаемое поведение:
- предупреждение об отсутствии наборов данных;
- успешное завершение;
- итог VALID;
- пустой stderr.

Все три отдельных процесса выдают одинаковые коды завершения, stdout и stderr.

### 3.2. Несколько недопустимых Schema references

В синтетической схеме размещены две внешние ссылки:
- первая — в $defs;
- вторая — в properties.

Политика валидатора запрещает внешние Schema references. Проверяется не только отказ, но и стабильность первой обнаруженной ошибки.

Ожидаемый первый адрес:

$.$defs.first_definition.$ref

Схема не загружается из сети. CLI должен завершиться кодом 2, не выдать содержимого в stdout и вернуть одинаковую диагностику в stderr во всех процессах.

### 3.3. Строгие отказы JSON

Отдельная матрица проверяет четыре входа:
- дублирующееся имя свойства;
- нестандартный числовой литерал NaN;
- числовое переполнение 1e999;
- потерю ненулевого значения при underflow 1e-999.

Для каждого варианта повторяются три независимых запуска. Сравниваются точный текст отказа, stderr, пустой stdout и код 2.

Тем самым проверяется воспроизводимость не только ошибок Schema, но и отказа на самом этапе чтения входных байтов.

### 3.4. Семантические ошибки вместе с предупреждениями

Создаётся структурно допустимый манифест, в котором:
- два набора имеют одинаковый dataset_id;
- calibration_status указан как unknown;
- orientation_status указан как partial.

Ожидаемый результат сочетает предупреждения в stdout с семантической ошибкой в stderr и кодом завершения 2. Проверяется неизменный порядок и байтовое содержание обеих групп сообщений.

### 3.5. Проверка файлов через --verify-files

Создаётся синтетический файл исходной записи. Его SHA-256 помещается в манифест. CLI вызывается с --verify-files.

Проверяется:
- успешное завершение с кодом 0;
- итог VALID для одного набора;
- пустой stderr;
- одинаковый вывод в трёх процессах;
- неизменность байтов манифеста и синтетического файла после всех запусков.

Это подтверждает воспроизводимость штатного пути файловой проверки, но не метрологическую достоверность тестовой записи.

## 5. Что доказано

Для перечисленных сценариев подтверждено:
- точное совпадение кодов завершения, stdout и stderr между тремя отдельными процессами;

- стабильность первого отказа при нескольких внешних ссылках Schema;
- стабильность сообщений строгого JSON-парсера;
- воспроизводимый порядок семантических предупреждений и ошибок;
- отсутствие изменения входных байтов при обычной проверке и при --verify-files;
- успешная работа полного CI-набора из 69 тестов на указанной среде.

## 6. Что не доказано

Результат не устанавливает:
- идентичность поведения во всех версиях Python и на всех операционных системах;
- стабильность каждого возможного сообщения при любом сочетании повреждений;
- эквивалентность локальных и сетевых файловых систем;
- корректность реальных приборных данных и калибровок;
- правильность геодезической привязки;
- физическую достоверность динамической или исторической модели Гизы.

Подтверждена программная воспроизводимость перечисленных сценариев в Python 3.11 на GitHub-hosted Ubuntu runner. Это не доказательство физической гипотезы и не проверка древней функции.

## 7. Следующая техническая граница

Матрица Ubuntu/Windows × Python 3.11/3.12/3.13 прошла целиком. Следующая версия не включалась: закреплённая зависимость NumPy 2.2.5 должна быть отдельно проверена на совместимость с Python 3.14. Не следует добавлять новую версию Python в матрицу, пока совместимость всех закреплённых библиотек не подтверждена.

Следующий самостоятельный слой:
1. проверить официальный диапазон поддержки Python для NumPy и jsonschema;
2. при необходимости обновить только обоснованно устаревшие зависимости;
3. повторить все 73 теста на Python 3.14 на обеих ОС;
4. сохранить прежние результаты 3.11–3.13 как контроль неизменности;
5. после кросс-версионной проверки оценить нагрузочные границы: большие файлы, большие манифесты и параллельные независимые запуски.

Эмпирическая граница остаётся отдельной: первичные временные ряды, полевые метаданные, калибровки и документированная геодезическая привязка пока не получены. Никакой синтетический CI-тест не заменяет эти материалы.
