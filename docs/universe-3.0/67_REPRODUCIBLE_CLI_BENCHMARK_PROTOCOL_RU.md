# Воспроизводимый benchmark-профиль приёмника GIZA PRIME

**Серия:** UNIVERSE 3.0 / GIZA PRIME  
**Документ:** 67  
**Дата:** 2026-11-25  
**Статус:** инструмент и четыре автоматические проверки добавлены; полный CI-набор из 80 тестов прошёл в восьми конфигурациях  
**Назначение:** задать измеряемый профиль времени работы CLI при изменении размера манифеста, объёма файла и уровня параллельности, сохраняя идентичность входов и происхождение результата.

## 0. Зачем выделен отдельный benchmark-слой

Документ 65 установил побайтную воспроизводимость диагностик и результатов. Документ 66 проверил увеличенный синтетический манифест, файл 4 МиБ и шесть одновременно работающих CLI-процессов.

Но устойчивость и производительность — разные характеристики.

- Тест устойчивости отвечает, завершилась ли проверка корректно и сохранились ли входные байты.
- Benchmark отвечает, сколько времени занял конкретный путь выполнения на конкретной аппаратной и программной среде и как меняется время при изменении одного параметра.

Время полного набора unit-тестов нельзя использовать как время одного запуска CLI. Поэтому создан отдельный инструмент, который замеряет end-to-end запуск валидатора и выдаёт машинно-читаемый JSON-отчёт.

## 1. Инструмент

Файл:

    tools/giza_spatial/benchmark_vibration_manifest_cli.py

Инструмент использует стандартную библиотеку Python и запускает штатный валидатор:

    tools/giza_spatial/validate_vibration_manifest.py

Он создаёт временный каталог, синтетический JSON-манифест и синтетические исходные файлы. Архивные данные, измерения Гизы и пользовательские файлы не читаются.

Входные файлы создаются детерминированно. Исходные байты записываются блоками, поэтому генерация крупного файла не требует держать весь файл в оперативной памяти.

## 2. Управляемые параметры

| Параметр | Диапазон / значение по умолчанию | Назначение |
|---|---|---|
| --datasets | 1–10000; default 1 | Число синтетических записей в манифесте |
| --file-size-bytes | 0–1 GiB; default 0 | Размер одного синтетического raw-файла |
| --verify-files | выключен | Включает реальную проверку существования, размера и SHA-256 через штатный CLI |
| --concurrency | 1, 2, 4 или 8; default 1 | Число одновременно запущенных процессов CLI |
| --repeat | 1–100; default 3 | Число измеряемых серий |
| --warmup | 0–10; default 1 | Число серий разогрева, не включаемых в статистику |
| --timeout-seconds | 1–3600; default 120 | Максимальное время одного процесса |
| --output | необязательный путь | Сохранение копии JSON-отчёта; тот же отчёт остаётся в stdout |

Параметр --file-size-bytes больше нуля требует --verify-files. При файловом измерении разрешён ровно один dataset. Это сделано намеренно: размер манифеста и объём файлового ввода измеряются раздельно, а не смешиваются в один неконтролируемый фактор.

Для проверки размера манифеста можно использовать несколько dataset без файлового чтения. В этих сценариях создаются пустые синтетические raw-файлы, а валидатор вызывается без --verify-files.

## 3. Что и как измеряется

### 3.1. Время одного процесса

Для каждого запуска фиксируется elapsed time от непосредственного вызова subprocess до получения завершённого процесса.

Это end-to-end время, которое включает:
- запуск Python;
- загрузку импортов;
- чтение манифеста;
- чтение и проверку JSON Schema;
- структурную и семантическую проверку;
- файловую проверку, если включён --verify-files;
- формирование stdout и stderr.

Это не изолированное время одной внутренней функции.

### 3.2. Время параллельной серии

В каждой измеряемой серии запускается указанное число CLI-процессов. Batch wall time измеряется от начала отправки группы до завершения последнего процесса.

Разница между индивидуальным временем процессов и временем всей серии позволяет увидеть стоимость параллельного исполнения, не подменяя одно измерение другим.

### 3.3. Повторные серии и разогрев

Сначала выполняются warm-up серии. Их результаты проверяются, но их время не входит в итоговую статистику.

Затем выполняется заданное число измеряемых серий. Для каждого набора собираются:
- минимум;
- медиана;
- максимум.

Порог производительности не встроен в программу. Инструмент фиксирует результаты, а критерии производительности должны задаваться отдельно после получения базовой серии на целевой среде.

### 3.4. Контроль идентичности и целостности

До запуска рассчитываются SHA-256:
- манифеста;
- каждого созданного исходного файла;
- JSON Schema;
- скрипта валидатора.

После всех серий повторно рассчитываются SHA-256 входов. Изменение любого манифеста или raw-файла приводит к отказу benchmark.

Внутри одной серии все процессы должны совпасть по:
- коду завершения;
- полным байтам stdout;
- полным байтам stderr.

То же сравнение выполняется между измеряемыми сериями. Различие выходных байтов не превращается в «медленный результат»: benchmark завершает работу с ошибкой.

## 4. Структура JSON-отчёта

Отчёт имеет формат:

    giza-prime-cli-benchmark-1.0

В нём содержатся следующие группы:

- runtime: ОС, описание платформы, версия Python, NumPy, jsonschema и необязательная ревизия Git;
- artifacts: SHA-256 валидатора и JSON Schema;
- configuration: число записей, размер манифеста, хеш, размер исходного файла, число файлов, объём данных, concurrency, warm-up, repeat и timeout;
- integrity: подтверждение неизменности входов и идентичности выходов;
- summary: число запусков, минимум, медиана и максимум индивидуального времени и batch wall time, SHA-256 проверенного stdout/stderr;
- measurements: отдельная запись на каждую измеряемую серию и времена отдельных процессов;
- limitations: ограничения того, что данная версия инструмента измеряет.

JSON сортируется по ключам и форматируется с отступами. Отчёт можно сохранить через --output и одновременно получить в stdout.

## 5. Примеры запуска

### 5.1. Размер манифеста

Из корня репозитория:

    python tools/giza_spatial/benchmark_vibration_manifest_cli.py --datasets 256 --concurrency 1 --repeat 5 --warmup 1 --output artifacts/manifest-256.json

### 5.2. Проверка одного файла 4 МиБ

    python tools/giza_spatial/benchmark_vibration_manifest_cli.py --datasets 1 --file-size-bytes 4194304 --verify-files --concurrency 1 --repeat 5 --warmup 1 --output artifacts/file-4mib.json

### 5.3. Сравнение параллельности

Каждый уровень запускается отдельной командой с одинаковыми остальными параметрами и сохраняется в отдельный JSON-файл:

    python tools/giza_spatial/benchmark_vibration_manifest_cli.py --datasets 256 --concurrency 1 --repeat 5 --warmup 1 --output artifacts/concurrency-1.json
    python tools/giza_spatial/benchmark_vibration_manifest_cli.py --datasets 256 --concurrency 2 --repeat 5 --warmup 1 --output artifacts/concurrency-2.json
    python tools/giza_spatial/benchmark_vibration_manifest_cli.py --datasets 256 --concurrency 4 --repeat 5 --warmup 1 --output artifacts/concurrency-4.json
    python tools/giza_spatial/benchmark_vibration_manifest_cli.py --datasets 256 --concurrency 8 --repeat 5 --warmup 1 --output artifacts/concurrency-8.json

Для сравнения между машинами и ОС нужно сохранять все JSON-отчёты, а не только итоговую медиану.

## 6. Автоматические проверки benchmark-инструмента

Создан файл:

    tests/giza_spatial/test_cli_benchmark.py

Четыре теста проверяют:
1. машинно-читаемый отчёт для манифеста с двумя dataset и concurrency 2;
2. файловую проверку 4096 байт с фактическим SHA-256;
3. отказ от смешения многозаписного манифеста с файловой нагрузкой;
4. запись JSON-копии по заданному пути при сохранении того же отчёта в stdout.

Проверяются также общая длительность benchmark, UTC-метка начала, число запущенных процессов, согласованность выходов и флаги неизменности входных файлов.

## 8. Что измеряется, а что остаётся вне инструмента

Данная версия фиксирует:
- end-to-end время одного CLI-процесса;
- batch wall time параллельной серии;
- медиану, минимум и максимум;
- объём манифеста и raw-файлов;
- контрольные SHA-256;
- идентичность диагностик и результата;
- программную среду и версии зависимостей.

Данная версия не измеряет:
- пиковую оперативную память;
- состояние дискового кэша и физическую скорость накопителя как отдельные величины;
- пропускную способность сети;
- конкурентную запись;
- исчерпание системных ресурсов;
- физическую реакцию сооружений или геологического основания.

Поэтому время, полученное на GitHub-hosted runner, нельзя использовать как норму для локальной станции, полевой лаборатории или промышленного узла. Для оценки памяти нужен отдельный кроссплатформенный метод с явной фиксацией источника метрики и частоты выборки.

## 9. Протокол получения базовой серии

Для каждого целевого компьютера:

1. Зафиксировать ОС, точную версию Python, NumPy, jsonschema, CPU, объём RAM, тип накопителя и режим питания.
2. Сохранить commit SHA, SHA-256 валидатора и Schema из отчёта.
3. Начать с повторяемых конфигураций: 1, 16, 64 и 256 dataset; отдельно — файлы 1, 4 и 16 МиБ; отдельно — concurrency 1, 2, 4 и 8.
4. Не смешивать размер манифеста и размер проверяемого файла в одной серии.
5. Выполнить не менее пяти измеряемых повторов после одного разогрева.
6. Сохранить полные JSON-отчёты и сравнивать медианы с разбросом, а не выбирать минимальное время.
7. Повторить одну и ту же конфигурацию после перезапуска процесса или машины, чтобы понять вклад состояния окружения.
8. Не устанавливать порогов до получения базовой серии на целевой аппаратной платформе.

Если результаты между сериями различаются, сначала исследуются среда выполнения, кэширование, файловая система и фоновые процессы. Нельзя автоматически объявлять причиной сам валидатор.

## 10. Следующий логический переход

Инструмент теперь способен воспроизводимо сравнивать обработку синтетических манифестов и файлов, но не является эмпирическим свидетельством о Гизе.

Следующая независимая работа разделяется на две линии:

**Программная:** добавить отдельный кроссплатформенный сбор пиковой памяти, установить профили размеров и параллельности на реальных целевых машинах, сохранять неизменяемые JSON-отчёты.

**Эмпирическая:** получить первичные временные ряды, полевые метаданные, паспорта приборов, калибровки, временную базу, системы координат и геодезические связи. Только после этого benchmark-приёмник можно наполнить реальными архивными данными; синтетическая проверка не подменяет их.
