**Статус:** строгий парсер включён для манифеста и JSON Schema; тесты CI пройдены

## 0. Исходное основание

Приёмный тракт получает не абстрактный Python-объект, а последовательность байтов, представленную как JSON-текст. До проверки JSON Schema парсер преобразует текст в объект. Поэтому правила чтения самого текста являются частью надёжности паспорта.

В стандартном Python json decoder есть два поведения, которые опасны для строгого реестра:
- по умолчанию принимаются числовые токены NaN, Infinity и -Infinity, хотя они не входят в грамматику JSON;
- при повторяющемся имени свойства стандартный разбор обычно оставляет последнее значение, не сообщая об этом вызывающему коду.

В результате исходный текст и полученный объект могут не соответствовать единственному однозначному представлению данных. Исправление выполнено на уровне общего загрузчика JSON.

## 1. Нормативное основание

RFC 8259 задаёт допустимые значения JSON и грамматику чисел. Раздел 3 перечисляет три логических/нулевых литерала — false, null и true — и не допускает другие буквальные имена. Раздел 6 прямо исключает Infinity и NaN из допустимых числовых представлений.

Раздел 4 рекомендует уникальность имён свойств объекта (SHOULD). При дублировании имён поведение принимающего программного обеспечения становится непредсказуемым: реализации могут вернуть последнее значение, сообщить об ошибке или передать все пары.

Для паспорта GIZA PRIME принято более строгое прикладное правило: повторяющиеся ключи запрещаются всегда, поскольку реестр должен иметь однозначное прочтение независимо от используемого JSON-парсера.

Источник: RFC 8259, The JavaScript Object Notation (JSON) Data Interchange Format:
- https://www.rfc-editor.org/rfc/rfc8259/
- https://datatracker.ietf.org/doc/html/rfc8259

## 2. Реализация

Файл tools/giza_spatial/validate_vibration_manifest.py получил три общие функции.

### 2.1. Запрет недопустимых числовых литералов

Функция _reject_nonstandard_json_constant(token) вызывает ValueError для NaN, Infinity и -Infinity.

Проверка выполняется самим JSON decoder на стадии чтения. Такие значения не доходят до JSON Schema, арифметики, координатных проверок или спектральной обработки.

### 2.2. Запрет повторяющихся имён объектов

Функция _reject_duplicate_json_keys(pairs) принимает пары ключ/значение каждого объекта:
- создаёт новый словарь;
- проверяет, не встречался ли ключ ранее;
- при повторе прекращает разбор с ValueError;
- сохраняет значение только при уникальном ключе.

Проверка применяется ко всем вложенным объектам, а не только к верхнему уровню. Поэтому одинаково обрабатываются дубли в корне, в project, в station, в channels и в других вложенных структурах.

### 2.3. Общий строгий загрузчик

Функция _strict_json_loads(raw) передаёт в json.loads:
- object_pairs_hook=_reject_duplicate_json_keys;
- parse_constant=_reject_nonstandard_json_constant.

Эта единая функция используется:
1. для чтения манифеста;
2. для чтения JSON Schema.

Таким образом, недопустимая неоднозначность не допускается ни в исходных данных, ни в формальном контракте.

## 3. Поведение CLI

Если манифест содержит NaN, Infinity или повтор ключа:
- JSON не преобразуется в Python-объект;
- CLI выдаёт сообщение о причине;
- команда завершается кодом 2;
- проверка схемы и семантическая обработка не запускаются.

Если повторяющийся ключ найден в файле JSON Schema:
- схема не принимается;
- CLI сообщает, что проверка схемы не может быть выполнена;
- код завершения равен 2.

Это намеренно fail-closed поведение: повреждённая или неоднозначная запись не становится частично действительным паспортом.

## 4. Тесты

Добавлены три автоматических теста.

### 4.1. Не-JSON числовые константы

CLI отдельно проверяет:
- NaN;
- Infinity;
- -Infinity.

Каждое значение отклоняется ещё при чтении манифеста.

### 4.2. Дублирующиеся имена в манифесте

Проверяются два случая:
- повтор ключа schema_version в корневом объекте;
- повтор ключа id во вложенном объекте project.

Оба случая завершаются кодом 2 и сообщением о повторяющемся JSON-ключе.

### 4.3. Дублирующееся имя в JSON Schema

CLI получает корректный тестовый манифест и схему, в которой ключ $schema указан дважды. Разбор схемы отклоняет файл до создания валидатора.

## 6. Границы и дальнейшее применение

Строгий парсер исключает некоторые неоднозначности представления, но не подтверждает:
- истинность заявленных метаданных;
- происхождение измерительных файлов;
- точность прибора;
- калибровку и ориентацию;
- корректность координат и высотной привязки;
- правильность спектральной обработки;
- физический смысл обнаруженного частотного пика.

После строгого разбора следуют уже установленные независимые этапы:
1. JSON Schema Draft 2020-12;
2. прикладные проверки;
3. проверка файлов при --verify-files;
4. отдельная метрологическая оценка;
5. воспроизводимая спектральная обработка;
6. независимая физическая валидация.

## 7. Следующая техническая граница

Теперь нужно проверить не только правильность входного JSON, но и корректность всего поведения CLI при ошибках структуры верхнего уровня:
- корень не является объектом;
- project не является объектом;
- datasets не является массивом;
- schema корректна по JSON, но некорректна как Draft 2020-12;
- схема с внешней или отсутствующей ссылкой не должна незаметно проходить.

Для каждого случая следует зафиксировать понятное сообщение и ожидаемый код завершения. Эмпирические файлы не добавляются в реестр без фактического получения.
