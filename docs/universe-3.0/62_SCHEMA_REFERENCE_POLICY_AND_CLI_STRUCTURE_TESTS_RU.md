## 0. Основание

Документы 59–61 зафиксировали исполняемую JSON Schema Draft 2020-12, матрицу покрытия и строгий разбор JSON-текста. Следующая граница находится внутри самого schema-контракта: схема может быть синтаксически корректным JSON, но структурно неправильной для Draft 2020-12, ссылаться на несуществующее определение или зависеть от внешнего адреса.

Приёмный инструмент должен завершаться определённой ошибкой, а не зависеть от случайной доступности внешнего документа или поведения resolver-а.

## 1. Политика ссылок

В JSON Schema разрешаются только:
- ссылка на корень текущей схемы: #;
- локальные JSON Pointer вида #/$defs/dataset;
- локальные JSON Pointer, разрешающиеся внутри того же документа.

Запрещаются:
- ссылки на HTTP(S) и любые другие внешние URI;
- относительные пути к сторонним schema-файлам;
- локальные указатели на отсутствующие определения;
- якорные fragment-ссылки вида #name, поскольку текущий приёмный контракт использует JSON Pointer и не реализует отдельное разрешение anchors.

Это ограничение относится к схеме, переданной для валидации, а не к содержимому данных. Оно исключает сетевую зависимость во время приёма и гарантирует, что используемые определения находятся в том же проверяемом файле.

## 2. Корректное определение областей, где ссылка является схемой

Сканирование не должно считать любое текстовое свойство "$ref" ссылкой на schema.

Например, в схеме:

    {
      "properties": {
        "payload": {
          "const": {
            "$ref": "https://example.invalid/literal"
          }
        }
      }
    }

значение $ref находится внутри const и является обычными сравниваемыми данными. Оно не должно запускать поиск внешней схемы или вызывать отказ.

Поэтому обход выполняется только по ключевым словам, содержащим реальные subschema:
- одиночные схемы: additionalProperties, unevaluatedProperties, propertyNames, contains, items, not, if, then, else, contentSchema и совместимый additionalItems;
- массивы схем: allOf, anyOf, oneOf, prefixItems;
- словари схем: $defs, definitions, properties, patternProperties, dependentSchemas.

При этом $ref, $dynamicRef и $recursiveRef выявляются только в действительном контексте schema object.

## 3. Реализация

В tools/giza_spatial/validate_vibration_manifest.py:
- добавлен обход schema-valued keywords, не заходящий внутрь const/default/examples и иных литеральных данных;
- внешние URI отвергаются до запуска Draft202012Validator;
- фрагмент локального JSON Pointer декодируется;
- escape-последовательности ~0 и ~1 проверяются;
- каждый сегмент указателя разрешается в словаре или индексируемом массиве;
- несуществующий сегмент приводит к ValueError с указанием места ссылки;
- сетевое получение внешних схем не выполняется.

После стандартной проверки Draft202012Validator.check_schema выполняется собственная проверка допустимости и разрешимости ссылок. Основной CLI уже обрабатывает ошибки схемы и возвращает код 2.

## 4. Проверка структуры CLI верхнего уровня

Добавлены случаи:
- корень JSON является массивом вместо объекта;
- project является массивом вместо объекта;
- datasets является объектом вместо массива;
- schema является корректным JSON, но содержит недопустимое значение ключа type для Draft 2020-12.

Все случаи должны возвращать ненулевой код (2) и диагностическое сообщение. Ошибочная структура не должна доходить до последующих этапов как действительный манифест.

## 5. Проверки ссылок и литеральных данных

Автоматически проверяются:
1. внешняя ссылка на schema отклоняется;
2. локальный JSON Pointer на отсутствующий $defs элемент отклоняется;
3. действующая схема проекта с локальными указателями остаётся допустимой;
4. текстовое свойство $ref внутри const трактуется как литеральное значение и не вызывает отказ;
5. ошибочная Draft 2020-12 схема не проходит этап check_schema.

Это разделяет два совершенно разных уровня: ссылку, управляющую разрешением schema, и данные, которые случайно содержат строку с именем $ref.

## 7. Границы политики

Текущая политика сознательно уже полной функциональности JSON Schema: она не разрешает внешние URI и именованные anchors. Для действующей схемы GIZA PRIME этого достаточно: все десять ссылок являются локальными JSON Pointer к определениям в $defs.

Если когда-либо потребуется схема с anchors или внешними переиспользуемыми определениями, это должно быть отдельное изменение:
- с явной политикой доверия к источникам;
- с фиксацией и хешированием внешних схем;
- без сетевого разрешения во время обычного CLI-приёма;
- с тестами локального кеша и отсутствующих зависимостей.

Расширять область разрешённых ссылок без такого контракта нельзя.

После строгого входного JSON, проверки Draft 2020-12, обязательных полей, enum и ссылок нужно завершить сверку семантического валидатора:
1. перечислить каждое правило Python, которое не выражено в JSON Schema;

4. зафиксировать единый порядок отказов и предупреждений.

После этого технический приёмный тракт можно считать готовым к заполнению первичными архивными файлами — но не к научной интерпретации до проверки калибровки, времени, ориентации и геопривязки.
