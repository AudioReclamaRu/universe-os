## 0. Исходное основание

После интеграции JSON Schema и семантического валидатора оставались два различия между формально допустимым паспортом и прикладной логикой.

Первое относилось к типу integer. В JSON Schema число 6000.0 считается целым, поскольку его математическое значение не имеет дробной части. Прежняя Python-проверка требовала именно экземпляр int и отвергала 6000.0. Таким образом, формально допустимое значение могло не пройти следующий слой.

Второе относилось к файловым путям. Проверялись одинаковые исходные строки путей, но разные строки могли после нормализации указывать на один и тот же файл.

Оба случая устранены и покрыты автоматическими тестами.

## 1. Математическая семантика integer

В Draft 2020-12 тип integer определяется не исключительно типом числового токена в языке реализации, а целым числовым значением. Поэтому:
- 6000 является integer;
- 6000.0 также является integer;
- 6000.5 не является integer;
- true не является integer, хотя в Python bool является подклассом int.

Проверка в валидаторе должна сохранять именно эту семантику, а не свойства конкретного языка программирования.

Источник:
- JSON Schema Draft 2020-12, Validation, §6.1.1: https://json-schema.org/draft/2020-12/json-schema-validation
- Python jsonschema type checker: https://python-jsonschema.readthedocs.io/en/stable/validate/

## 2. Исправление в Python

В tools/giza_spatial/validate_vibration_manifest.py добавлена единая функция _is_integer(value).

Она возвращает true:
- для целых Python int, кроме bool;
- для конечных float, у которых is_integer() равно true.

Она возвращает false:
- для bool;
- для дробных float;
- для NaN и бесконечности;
- для строк, массивов, объектов и null.

Функция используется для:
- acquisition.sample_count;
- file.size_bytes при проверке фактических файлов.

При расчёте ожидаемой длительности значение sample_count приводится к int после проверки целочисленности. Файловый размер также сравнивается как целое число.

Это устраняет зависимость от того, каким числовым токеном в JSON было записано математически целое значение.

## 3. Подтверждённые тесты числовой семантики

Добавлены два сценария.

### 3.1. sample_count с десятичной записью целого числа

Значение 6000.0:
- принимается JSON Schema как integer;
- принимается семантическим валидатором;
- используется в проверке длительности;
- не порождает ложной ошибки или предупреждения.

### 3.2. size_bytes с десятичной записью целого числа

В тестовом наборе создаётся временный файл. В манифест записывается размер в виде float, например 28.0:
- схема принимает значение как integer;
- валидатор сравнивает его с фактическим размером;
- CLI-проверка байтов завершается без ошибок.

Булевы и дробные значения не разрешаются как целые. Проверка конечности также сохраняется.

## 4. Каноническая идентичность файлового пути

Ранее file_paths отслеживал уникальность исходных строк. Это не обнаруживало такие пары:

- raw/station01.mseed
- raw/./station01.mseed

Обе строки представляют один нормализованный путь.

Теперь для каждого относительного пути вызывается _safe_relative_path, который:
1. отклоняет пустые и абсолютные пути;
2. разрешает путь относительно объявленного корня;
3. нормализует точечные сегменты;
4. разрешает символические ссылки;
5. отклоняет выход за пределы корня.

Затем валидатор сравнивает полученный canonical Path с ранее зарегистрированными путями внутри того же набора. Если два разных file record разрешаются в один Path, выдаётся ошибка:

    multiple file records resolve to the same path

Проверка выполняется и без --verify-files. Для обнаружения совпадения расположения не требуется чтение содержимого файла.

Проверка исходных строк также остаётся: она даёт более прямое сообщение для буквального дубликата. Каноническая проверка закрывает эквивалентные записи после нормализации.

## 5. Абсолютные пути разных операционных систем

В Unix-подобной среде Path('C:\data\file') может выглядеть как относительная строка, поскольку это синтаксис Windows.

Чтобы паспорт не менял смысл при переносе между системами, валидатор дополнительно анализирует PureWindowsPath. Отклоняются:
- POSIX absolute paths;
- Windows drive paths;
- Windows UNC paths;
- Windows paths, содержащие drive prefix даже без ведущего разделителя.

Таким образом, Windows-путь не может незаметно превратиться в относительное имя файла при проверке на Linux.

Смысл file.path остаётся однозначным: только безопасный относительный путь внутри заданного корня данных.

## 6. Новые автоматические тесты

Добавлены четыре теста:
1. целочисленное значение sample_count в формате float соответствует и JSON Schema, и семантической проверке;
2. целочисленный float size_bytes совпадает с фактическим размером временного файла;
3. два различных пути, нормализующиеся в один файл, отклоняются;
4. Windows drive и UNC absolute paths отклоняются при выполнении на POSIX.

В совокупности эти тесты проверяют и формальную семантику числового типа, и фактическую идентичность файловых референтов после нормализации.
