## 0. Принцип разделения

**Совокупное Вненаблюдаемое и есть ВСЕЛЕННАЯ. Наблюдаемое + Ненаблюдаемое — наше понимание ЕЁ.**

В приёмнике динамических данных различаются четыре уровня:

1. **Структура:** соответствует ли JSON формальной схеме Draft 2020-12.
2. **Семантика:** согласованы ли значения и связи внутри описания измерения.
3. **Файловая целостность:** существуют ли заявленные файлы и совпадают ли их байты с паспортом.
4. **Научная состоятельность:** подтверждены ли калибровка, ориентация, геопривязка, качество измерения и физическая интерпретация.

Первые три уровня частично автоматизированы. Четвёртый требует первичных записей, метрологической документации, воспроизводимой обработки и независимой физической проверки. Прохождение схемы не означает правильность измерения.

## 2. Согласованные ограничения

После интеграции JSON Schema и дополнительной сверки устранены следующие расхождения.

### 2.1. Модель прибора

Ранее схема разрешала null для instrument.model, тогда как прикладной валидатор требовал непустое значение. Теперь схема требует строку с minLength 1. Если точная модель неизвестна, это следует записывать явным текстовым значением unknown, а не null или пустой строкой.

### 2.2. Статусы качества

Ранее Python-валидатор требовал пять статусов качества, но схема не делала все пять полей обязательными. Теперь quality.required перечисляет:
- status;
- calibration_status;
- orientation_status;
- timing_status;
- coordinate_status.

Допустимые значения остаются ограниченными enum. Значения unknown и partial допускаются, но обозначаются как предупреждения, а не как подтверждённое качество.

### 2.3. Enum и небезопасные типы

Сравнение значений с множествами разрешённых строк теперь предваряется проверкой типа. Поэтому массив, объект или другой неверный JSON-тип в поле enum превращается в обычное сообщение об ошибке, а не в TypeError.

Покрыты source.origin, instrument.sensor_type, acquisition.time_standard, channel.component, channel.unit, file.role, file.file_format и статусы quality.

### 2.4. Значение default для трёх компонент

В JSON Schema у require_three_components указано default: true. Само по себе JSON Schema не изменяет входной документ и не подставляет это значение автоматически. Прикладной валидатор реализует то же правило явно через dataset.get("require_three_components", True).

Таким образом:
- поле отсутствует — требование трёх компонент включено;
- поле true — требование включено;
- поле false — набор может быть неполным, если это намеренно описано;
- значение неправильного типа отклоняется схемой.

## 3. Ограничения, которые проверяются только одним слоем

### 3.1. Schema-only ограничения

Схема выполняет часть структурных проверок, которые не дублируются прикладной логикой:
- непустой dataset.title;
- наличие ключа instrument.manufacturer (само значение может быть null);
- форматы URI и отдельных дат;
- допустимые типы необязательных полей;
- запрет незадекларированных свойств;
- числовые границы uncertainty и некоторых параметров.

Это осознанное распределение: Schema отвечает за форму и объявленные диапазоны, прикладной валидатор — за отношения и согласованность.

### 3.2. Semantic-only ограничения

Прикладной валидатор отвечает за:
- уникальность dataset_id, channel_id и file_id;
- отсутствие дублирования основных компонент;
- обязательность роли raw;
- уникальность путей внутри набора;
- существование каждой ссылки derived_from_file_ids;
- запрет абсолютных путей и выхода за корень, в том числе через разрешение символических ссылок;
- сравнение end_time с start_time;
- предупреждение о расхождении временного интервала и sample_count/sample_rate.

Эти ограничения трудно выразить обычными локальными JSON Schema-проверками, поскольку они требуют сравнения нескольких элементов, значений или внешней файловой системы.

### 3.3. File-only проверки

Фактическое существование, размер и SHA-256 проверяются лишь тогда, когда пользователь явно указывает --verify-files.

Без этого параметра:
- SHA-256 всё равно должен иметь допустимую форму;
- size_bytes должен иметь допустимый тип и диапазон;
- наличие байтов на диске не утверждается;
- совпадение хеша с байтами не утверждается.

Это намеренно: реестр может быть принят для первичной регистрации метаданных до получения полного локального архива, но такой пакет нельзя объявлять прошедшим проверку целостности.

## 6. Граница научной валидации

Даже полностью допустимый манифест не доказывает:
- что датчик действительно был установлен в заявленном месте;
- что его оси действительно соответствуют Z/N/E;
- что калибровка соответствует периоду измерений;
- что временная синхронизация была точной;
- что обработка не удаляет значимые процессы;
- что спектральный максимум является собственной модой сооружения;
- что современный режим существовал в прежнем состоянии Гизы;
- что режим связан с исторической функцией комплекса.

Для таких заключений нужны первичные измерительные файлы, метрологические документы, полевые журналы, независимая геодезия, повторные записи и модальная идентификация.
