## 0. Основание

Документ 52 фиксировал существенное разделение: JSON Schema описывала структуру паспорта, а исполняемый Python-валидатор проверял прикладные правила и файловое происхождение. До интеграции CLI не запускал движок JSON Schema, поэтому существование схемы ещё не означало, что каждый приёмный запуск реально проверял соответствие ей.

Это различие устранено. Теперь CLI последовательно выполняет:
1. чтение JSON;
2. проверку самой схемы Draft 2020-12;
3. проверку содержимого по схеме;
4. прикладные проверки манифеста;
5. при явном запросе — проверку наличия файлов, размера и SHA-256.

Формальная схема, прикладная семантика и проверка физических файлов остаются разными слоями. Успешное прохождение одного слоя не заменяет остальные.

## 1. Зависимость

Файл requirements-giza-signal.txt теперь закрепляет:

    numpy==2.2.5
    jsonschema[format-nongpl]==4.26.0

Версия jsonschema 4.26.0 опубликована на PyPI 7 января 2026 года; пакет поддерживает Draft 2020-12 и Python от 3.10. Поэтому она совместима с Python 3.11, используемым текущим GitHub Actions runner.

Источники:
- https://pypi.org/project/jsonschema/4.26.0/
- https://python-jsonschema.readthedocs.io/en/stable/

Дополнительный набор format-nongpl нужен для проверки форматов, объявленных в схеме, в частности date-time, date и uri. Проверка формата включена через FormatChecker; это не остаётся только описательной аннотацией.

## 2. Реализация

Файл tools/giza_spatial/validate_vibration_manifest.py получил следующие элементы.

### 2.1. Единая точка входа в проверку схемы

Функция validate_json_schema_payload(payload, schema_path):
- считывает указанную JSON Schema;
- выполняет Draft202012Validator.check_schema;
- создаёт Draft202012Validator;
- включает FormatChecker;
- собирает все ошибки валидации;
- сортирует их по пути внутри документа;
- возвращает сообщения с адресом ошибки, например $.datasets[0].acquisition.start_time.

### 2.2. Путь к схеме

По умолчанию используется:

    schemas/giza_ambient_vibration_manifest.schema.json

Путь вычисляется относительно расположения исполняемого файла в репозитории, поэтому запуск не зависит от текущего каталога оболочки.

Параметр --schema позволяет передать другую схему явно. Это облегчает отдельную проверку новой версии контракта, не меняя исходный файл.

### 2.3. Порядок проверок CLI

Команда теперь:
- проверяет JSON Schema;
- затем выполняет прикладные проверки;
- выводит все найденные ошибки;
- завершает работу кодом 2 при любой ошибке;
- возвращает статус VALID только если оба уровня не нашли ошибок.

Предупреждения о неполных или неизвестных метаданных остаются предупреждениями и не заменяются выдуманными значениями.

Параметр --verify-files по-прежнему включает отдельную проверку реальных файлов по относительным путям, размерам и SHA-256. Формальная Schema-проверка не подменяет эту операцию.

## 3. Новые автоматические тесты

К существующему набору добавлены четыре теста.

### 3.1. Пустой шаблон

Проверяется, что:
- JSON Schema сама проходит проверку Draft 2020-12;
- пустой шаблон из examples/giza_spatial/ambient_vibration_manifest.template.json соответствует контракту.

Пустой реестр с нулём наборов остаётся допустимым состоянием приёма.

### 3.2. Полный синтетический набор

Проверяется, что тестовый паспорт с тремя компонентами, источником, станцией, прибором, временем, файлами и статусом качества соответствует схеме.

Все координаты, измерения и хеши в этом тесте синтетические. Он проверяет структуру контракта, а не сведения о реальной станции.

### 3.3. Проверка формата времени

Искусственно заданная невозможная календарная дата должна быть отклонена FormatChecker как недопустимый date-time.

Это отдельная проверка формата. Прикладной валидатор дополнительно проверяет временную зону, порядок временных отметок и согласованность длительности с частотой дискретизации и числом отсчётов.

### 3.4. Проверка CLI на лишнее поле

В манифест добавляется корневое свойство, отсутствующее в контракте additionalProperties=false. CLI должен:
- сообщить ошибку с путём JSON Schema;
- вернуть код завершения 2;
- не объявить манифест допустимым только потому, что прикладные проверки не обнаружили это свойство.

Этот тест доказывает, что формальная схема действительно включена в основной приёмный путь.

### 4.8. Строгий разбор манифеста и самой схемы

Стандартный Python JSON decoder по умолчанию может принимать числовые токены NaN/Infinity и не выявлять дубли ключей. Для однозначного приёма введён общий строгий загрузчик, используемый для манифеста и JSON Schema. Он:
- отклоняет NaN, Infinity и -Infinity;
- отклоняет дубли ключей в корневых и любых вложенных объектах;
- прекращает приём до проверки схемы и семантики при неоднозначном исходном тексте;
- аналогично отклоняет сам файл JSON Schema, если в нём есть повторяющиеся ключи.

Основание — RFC 8259: раздел 6 исключает NaN и Infinity из JSON number; раздел 4 рекомендует уникальные имена объектов и отмечает непредсказуемое поведение при дублировании. Для научного паспорта выбрана строгая политика: дубли запрещены.

## 6. Оставшаяся граница согласованности

JSON Schema и прикладной валидатор имеют разные обязанности.

JSON Schema определяет:
- допустимую структуру;
- обязательные поля;
- типы;
- перечисления;
- числовые диапазоны;
- регулярные выражения;
- ссылки между определениями;
- форматы, которые проверяет FormatChecker.

Прикладной валидатор определяет:
- уникальность ID в пределах набора;
- временную последовательность;
- сравнение длительности с числом отсчётов и частотой;
- наличие обязательных компонентов;
- наличие сырого файла;
- уникальность путей;
- внутренние связи производных файлов;
- разрешённые пути и выход за корень данных;
- соответствие размера и SHA-256 фактическим байтам;
- предупреждения о неполноте метрологических сведений.

Некоторые правила намеренно существуют в обоих слоях — например, положительность частоты дискретизации. Матрица покрытия зафиксирована в документе 60; граничные сценарии, enum-паритет, required-поля и семантика default защищены автоматическими тестами. Строгий разбор JSON описан в документе 61. Следующая задача — проверить ошибки верхнеуровневой структуры: не-object корня, неверного типа project/datasets и структурно некорректной схемы Draft 2020-12.

## 7. Применение к GIZA PRIME

Теперь реестр имеет исполняемый структурный контракт и отдельные проверки происхождения и целостности. Это снижает вероятность того, что файл с пропущенными полями или неизвестной структурой будет принят как полноценный паспорт.

Но корректный JSON ещё не означает корректное измерение. Источник, станция, прибор, синхронизация, единицы, ориентация, координатная система и калибровка должны подтверждаться первичными материалами.

Пока исходные записи исследования не получены, пустой шаблон остаётся пустым, а синтетические тесты сохраняют статус синтетических.
