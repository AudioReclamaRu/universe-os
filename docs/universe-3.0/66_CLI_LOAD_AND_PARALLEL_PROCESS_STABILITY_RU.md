## 0. Связь с предыдущими проверками

Документы 61–65 закрепили строгий разбор JSON, выполнение JSON Schema, семантические и файловые ограничения, стабильный порядок диагностик и побайтную воспроизводимость результата между отдельными процессами.

Документ 65 закрыл матрицу отказов и положительных сценариев. Следующий вопрос — сохраняются ли те же свойства при увеличении объёма входа и параллельном обращении к одним и тем же файлам.

Для этого добавлены три теста в файл tests/giza_spatial/test_cli_determinism.py.

Новые тесты не меняют рабочий валидатор. Все входы синтетические и предназначены только для проверки программной процедуры.

## 1. Большой манифест: 256 наборов данных

Тест test_large_manifest_is_byte_stable_across_hash_seeds создаёт один JSON-манифест с 256 отдельными наборами данных.

Для каждого набора формируются собственные:
- dataset_id;
- station_id;
- file_id;
- относительный путь к исходному файлу;
- название набора.

Структура каждого набора основана на том же валидном трёхкомпонентном шаблоне, который используется в обычных тестах. Проверяется полный путь чтения, JSON Schema и семантической проверки.

Размер сериализованного манифеста должен превышать 100 000 байт. Один и тот же файл трижды передаётся отдельным процессам Python с PYTHONHASHSEED 1, 73 и 987654321.

Критерии:
- код завершения 0;
- итог VALID: 256 dataset(s);
- пустой stderr;
- побайтно одинаковые stdout и stderr;
- неизменность исходного файла манифеста.

Это проверяет корректность на увеличенном наборе записей, но не устанавливает предельную вместимость валидатора.

## 2. Крупный файл исходной записи: 4 МиБ

Тест test_large_raw_file_hash_is_byte_stable_and_input_is_unchanged создаёт синтетический файл размером ровно 4 МиБ.

В манифест включаются:
- SHA-256 файла;
- size_bytes;
- стандартный относительный путь внутри корня данных;
- роль raw.

CLI запускается с параметром --verify-files в трёх отдельных процессах с разными PYTHONHASHSEED.

Критерии:
- код завершения 0;
- файл проходит проверку SHA-256;
- фактический размер совпадает с size_bytes;
- итог VALID: 1 dataset(s);
- stdout и stderr стабильны;
- байты файла и манифеста не изменяются.

Проверка размера выполняется внутри срока жизни временного дерева данных. Это важно: после завершения временного контекста система закономерно удаляет созданные файлы, и обращение к ним после очистки не является проверкой поведения CLI.

## 3. Параллельное чтение шестью CLI-процессами

Тест test_parallel_cli_processes_produce_identical_results одновременно запускает шесть независимых процессов валидатора. Максимальное число одновременных рабочих потоков — четыре.

Каждый процесс:
- использует один и тот же манифест;
- читает один и тот же синтетический исходный файл;
- запускает --verify-files;
- получает собственный PYTHONHASHSEED.

Значения hash seed различаются. Результаты сравниваются по трём компонентам:
1. коду завершения;
2. полным байтам stdout;
3. полным байтам stderr.

До параллельной серии и после её завершения сверяется SHA-256 манифеста и файла.

Критерии:
- все шесть процессов завершаются кодом 0;
- все три выходных компонента совпадают побайтно;
- итог содержит VALID: 1 dataset(s);
- stderr пуст;
- входные байты не изменены.

Проверяется параллельное чтение. Это не тест конкурентной записи и не доказательство безопасности одновременной модификации файла.

## 5. История исправления тестовой фикстуры

Первый стресс-прогон — run 45670281890 — выявил одну ошибку в самом тесте крупного файла.

CLI успешно выполнил проверку файла и завершил межпроцессную серию. Затем тест обращался к raw_path.stat() уже после выхода из TemporaryDirectory. К этому моменту временный каталог был штатно удалён, поэтому возник FileNotFoundError.

Проверка размера перенесена внутрь временного контекста. Исправление зафиксировано отдельным коммитом 193b0c1ebbe4a87e8ef017787907ecbb1ba451c8. После него полный прогон из 76 тестов прошёл во всех восьми конфигурациях.

Это была ошибка времени жизни тестовой фикстуры, а не ошибка SHA-256, файловой проверки или рабочего валидатора.

- шесть параллельных процессов могут одновременно читать один и тот же манифест и файл;
- параллельные процессы дают одинаковые коды завершения и выходные байты;
- проверенные входные файлы не изменяются;
- полный набор из 76 тестов прошёл на двух ОС и четырёх версиях Python.

## 7. Что не доказано

Нельзя переносить этот результат на:
- произвольный размер манифеста или произвольное число наборов данных;
- произвольный объём исходного файла;
- неограниченное число одновременных CLI-процессов;
- конкурентную запись или замену входного файла во время чтения;
- сетевые файловые системы и нестандартные хранилища;
- поведение при исчерпании памяти, диска или дескрипторов;
- реальные измерительные данные, калибровку и физическую корректность.

Время из таблицы относится ко всему набору 76 тестов на конкретном runner. Оно не является отдельным benchmark-измерением времени одного CLI-запуска.

## 8. Следующая техническая граница

Следующий шаг — создать отдельный воспроизводимый benchmark-протокол, который будет отдельно измерять:
1. время чтения и проверки манифеста;
2. время --verify-files для нескольких размеров файла;
3. время для нескольких размеров манифеста;
4. пиковую память процесса;
5. время при параллельности 1, 2, 4 и 8 процессов;
6. разброс результатов между повторными сериями.

Для каждого измерения должны фиксироваться ОС, версия Python, версия NumPy, версия jsonschema, параметры входа и контрольный хеш исходных данных.

Пороговые значения производительности нельзя назначать до получения базовой серии измерений. Синтетические измерения должны оставаться отделёнными от реальных архивных временных рядов.
